# Рабочий ритм в plateful

## Коммит и пуш — на каждом логическом куске

Работаем прямо в `main`, без веток и PR. **Коммитить и пушить сразу, как только
кусок работы закончен и проверен** — не копить изменения до конца сессии.

Логический кусок — это то, что можно откатить целиком, не сломав остальное:
одна миграция, один экран, один слой, одно исправление бага с тестом.

Почему: если что-то пойдёт не так, откат должен стоить один `git revert`,
а не разбор мешанины из десяти несвязанных правок.

Порядок: правка → сборка/тесты зелёные → коммит → пуш → проверить CI.
Не пушить то, что не собирается или не проходит тесты локально.

Сообщение коммита — по-английски, без строк атрибуции. Первая строка — что
сделано, дальше почему, если причина неочевидна.

## Проверка — тестами и логами, не глазами

Скриншоты симулятора для проверки **не делать**. Симулятор — только запустить
и прочитать логи:

```bash
xcrun simctl launch booted com.anluch.plateful
xcrun simctl spawn booted log show --last 60s --info --debug \
  --predicate 'subsystem == "com.anluch.plateful"' --style syslog
```

Без `--info --debug` сообщения уровня `info` не видны, и успешная работа
выглядит как молчание — на этом уже спотыкались.

Ручное тестирование делает uladluch. Задача — покрыть автотестами столько,
чтобы его участие требовалось как можно реже. Каждый найденный баг
закрывается тестом в том же коммите.

Тесты: Swift Testing в `platefulTests/`. Логику, которую можно проверить без
UI, выносить в чистые типы и покрывать напрямую.

```bash
xcodebuild test -project plateful.xcodeproj -scheme plateful \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'
```

## Хук перед пушем

`.githooks/pre-push` не пускает то, что не собирается или не проходит тесты.
Ставится один раз на машине:

```bash
git config core.hooksPath .githooks
```

Гоняет только то, что задето пушем: бэкенд-тесты при правках в `backend/`,
iOS-тесты при правках приложения, сверку сид-пака при правках конвейера.
Обойти — `git push --no-verify`, и это должно быть осознанным действием.

Хук лежит в репозитории, а не в `.git/hooks`, чтобы пережить свежий клон.
До него единственной проверкой был CI, то есть о поломке узнавали уже
после пуша.

## CI

- `backend-ci` — на изменения в `backend/`: собрать пак, сверить с файлом в бандле.
- `ios-ci` — на изменения в приложении: тесты на macOS-раннере.
  Минуты тарифицируются ×10, поэтому фильтр по путям жёсткий.
- После пуша дождаться результата: `gh run watch $(gh run list --limit 1 --json databaseId -q '.[0].databaseId')`.

CI уже ловил то, что локальный прогон пропускал (разное поведение повреждённых
байтов). Красный CI — чинить сразу, не откладывая.

## Секреты

`SUPABASE_ACCESS_TOKEN` — в GitHub Secrets, для `publish-pack`. Локально ничего
не нужно: `supabase` CLI авторизован и линкован, `db query`/`storage cp`
работают по его токену.
